## Context

[SPEC-0298](./0298-agentic-mvp-cheap-durable-quiet-conductor.md) counts 34 `rebase_conflict`
parks out of about 98 and asks to classify them by file and fix the dominant cause at the
source. The classification, from the campaign ledgers under
`~/.local/share/wt/agentic/campaigns` and `wt campaign export` on 2026-10-30:

- **By time.** 33 of the 34 parks happened on 2026-10-25 and one on 2026-10-26 22:01. There
  have been **none since 2026-10-27**, over 58 closes.
- **By cause.** 26 of the 34 came before the in-queue `conflict_resolver`
  ([SPEC-0221](./0221-rebase-conflict-resolver-persona.md)) was running: the runner parked
  and the conductor hand-spawned a resolver sub-agent each time (its notes say so). The
  other 8 carry `(resolver: 2 attempts, …)` in the detail. In all 8 the resolver *had*
  resolved the conflict, and the runner's verification rejected the result (commit-count
  accounting, IDEA-328), which SPEC-0252 and SPEC-0259 fixed. The conductor's notes on
  each one read "resolver correct but count check rejected".
- **By file.** `docs/LEDGER.md` was in 28 of the 34 conflicts, but never alone: a step
  that conflicts only on `merge.regenerate` paths is regenerated by `gitops.rebase`
  (`src/wt/agentic/gitops.py:367-406`, SPEC-0191) and never parks. That happened 44 times
  since 2026-10-27. The ledger rides along with real code conflicts:
  `tests/test_agentic_queue.py` 14, `src/wt/agentic/queue.py` 11,
  `tests/test_agentic_profiles.py` 10, `profiles.py` 6, and a long tail. CLI registration
  modules (`src/wt/cli.py`, `cli_campaign.py`) appear 4 times in total, so they are not a
  dominant cause.
- **Since 2026-10-27** the resolver was dispatched 16 times and all 16 resolutions were
  verified (`rebase_resolved`). 47 resolver runs to date cost $20.22 in total.

So the dominant historical cause, a missing resolver and then a broken verification, is
already fixed. Three paths to a `rebase_conflict` park remain in the code, and each of
them has fired at least once:

1. **Base churn counted as conflict failure.** `_dispatch_resolver` (`queue.py:2329-2355`)
   stops after `MAX_RESOLVE_ATTEMPTS` (2, `queue.py:102`) resolver runs per entry into
   CLOSING, counting *verified* runs too. When main moves and conflicts again after each
   verified resolution, the campaign parks `rebase_conflict` with "(resolver: 2 resolutions
   verified; the base moved and conflicted again)" (`_spent_resolver_park`,
   `queue.py:2358-2372`). Nothing failed; the base was busy. That is `base_moving`, which
   [SPEC-0302](./0302-routine-parks-decided-by-the-queue.md) makes routine.
2. **The resolver blocked by the cost cap.** `plan_step` checks the cap before a resolve
   step (`queue.py:221-226`). SPEC-0225 parked `cost_cap` at $13.88 of $15 because "a
   conflict_resolver run may cost $2.00". A campaign that already passed its gates and
   review then waits for the conductor over one cheap run (the median resolver run costs
   about $0.43).
3. **The resolver really failed twice.** This is a genuine decision and stays the
   conductor's (`parked.rebase_conflict` row of `/wt-conduct`).

## Goals / Non-goals

**Goals**
- A close whose resolver runs were all verified, but whose base kept moving, parks
  `base_moving` (routine, SPEC-0302), not `rebase_conflict`.
- A resolver run is never blocked by the campaign cap within a small, explicit close
  allowance.
- `rebase_conflict` then means only that the resolver failed, or that the project opted out
  with `merge.resolver: false`.
- Conflict pressure is visible per campaign in `wt campaign export`, so a returning
  `rebase_conflict` or resolver trend shows up in data rather than in conductor turns.

**Non-goals**
- Reducing how often code conflicts happen (splitting `queue.py` or the large test modules).
  The evidence shows the resolver handles them, and cheaply. Splitting hot modules is a
  refactor with its own spec if the exported pressure ever shows a need.
- Merge drivers for generated files. Generated-only steps already never park, and in mixed
  steps the resolver takes a side and regenerates (its prompt's *Generated files* section).
- Changing the resolver persona, its prompt or its verification (SPEC-0221/0252/0259 stand).

## Decision

1. **Separate the two budgets.** `closing.resolve_failed.n` (already kept by
   `_apply_resolve`, `queue.py:2415`) is the failure budget: at most `MAX_RESOLVE_ATTEMPTS`
   (2) **failed** resolver runs per entry into CLOSING. A new bound, `MAX_RESOLVE_RUNS = 4`,
   caps all resolver runs (verified or not) per entry into CLOSING, so a base that never
   settles cannot loop forever. `_dispatch_resolver` dispatches while
   `failed < MAX_RESOLVE_ATTEMPTS and runs < MAX_RESOLVE_RUNS`.
2. **Name the park after its cause.** When the dispatch is refused:
   - because failed runs reached `MAX_RESOLVE_ATTEMPTS`, it parks `rebase_conflict` with
     today's detail (`_spent_resolver_park`);
   - because runs reached `MAX_RESOLVE_RUNS` with the last run verified, it parks
     **`base_moving`** with detail `"<base> moved and conflicted again after <k> verified
     resolutions"` and `resume_to: CLOSING`. SPEC-0302 then auto-resumes it with backoff,
     and the resume resets both budgets (entering CLOSING resets `closing`,
     `queue.py:842`).
3. **Close allowance for the resolver.** In `plan_step`'s CLOSING branch, the resolver's
   cap check uses `cap_usd + resolver_allowance_usd`. `resolver_allowance_usd` is
   `merge.resolver_allowance_usd` in the project config, defaulting to the profile's
   `conflict_resolver.max_budget_usd` × `MAX_RESOLVE_ATTEMPTS` ($4.00 with the balanced
   profile). The allowance is not added to `cost.cap_usd`. Spend over the cap is recorded
   as it happens, and the export shows it (`cost_cap_frac` > 1). Beyond the allowance the
   park is the ordinary `cost_cap`. A `finding` (`severity: info`, `gate: rebase`, title
   "resolver ran on the close allowance") is appended whenever a resolve step starts above
   the plain cap, so the overspend is auditable.
4. **Export conflict pressure.** `wt campaign export` campaigns rows gain, appended per the
   `wt.campaign.export.v1` contract: `rebase_regenerated` (count of "generated files
   regenerated during rebase" findings), `resolver_dispatches` (count of "rebase conflict;
   resolver dispatched" findings), `rebase_resolved` (count of `rebase_resolved` events) and
   `resolver_allowance_usd` (the spend above `cap_usd` during resolve steps, or 0).

## Design

- `src/wt/agentic/queue.py`:
  - `MAX_RESOLVE_RUNS = 4` next to `MAX_RESOLVE_ATTEMPTS`.
  - `_dispatch_resolver` returns `"dispatched" | "failed_out" | "runs_out" | "no"`
    (replacing the bool). `no` covers today's other refusals (opt-out, missing
    `pre_head`/`target_sha`, `merge_base` failure) and parks `rebase_conflict` as today.
    Its caller (`queue.py:2075-2079`) maps `failed_out` and `no` to
    `_spent_resolver_park` / `rebase_conflict`, and `runs_out` to the `base_moving` park of
    Decision 2.
  - `_apply_resolve` (`queue.py:2379-2428`): its final park after a failed run checks
    `resolve_failed.n` against `MAX_RESOLVE_ATTEMPTS` instead of `resolve_attempts`, so a
    verified run followed by one failure gets a retry. The `resolve_attempts` counter stays
    as the run count for `MAX_RESOLVE_RUNS`.
  - `_resolver_allowance(project_cfg, profile) -> float` and, in `plan_step`'s CLOSING
    branch, `_cap_blocks` is called on a shallow copy of the state whose `cost.cap_usd` is
    raised by the allowance. The "resolver ran on the close allowance" finding is appended
    in the resolve step's apply when `cost.total_usd` exceeded the plain cap at dispatch.
- `src/wt/agentic/project.py`: `merge.resolver_allowance_usd` (number ≥ 0, optional) in the
  project schema next to `merge.resolver` (`project.py:40`).
- `src/wt/agentic/campaign_export.py`: the four columns in the campaigns table schema and
  `campaign_row`, counted from the ledger events the row already reads.
- `skills/wt-conduct/SKILL.md`: the `parked.rebase_conflict` row drops the "two verified
  resolutions … overtaken by a base move" case (that is now `base_moving`) and says the
  park means the resolver failed twice or the project opted out.

## Alternatives considered

- **A `.gitattributes` merge driver for `docs/LEDGER.md`.** The ledger never caused a park on
  its own; a driver would only remove it from mixed conflicts that the resolver already
  handles by taking a side and regenerating. It adds a repo-config dependency for no change
  in parks.
- **Split `queue.py` / `tests/test_agentic_queue.py` to cut conflict incidence.** These are
  the top real-conflict files, but resolutions since 2026-10-27 are 16 of 16 verified at
  about $0.43 a run. A large refactor is not justified by that cost; the exported
  `resolver_dispatches` will show if it becomes one.
- **Raise `MAX_RESOLVE_ATTEMPTS` to 4.** That would keep failed resolutions retrying too,
  at a cost, when two failures are a real signal for the conductor. Splitting the budgets
  keeps the failure signal and removes the false one.
- **Exempt the resolver from the cap entirely.** An unbounded exemption would hide a
  resolver that loops; a fixed allowance tied to the attempt budget bounds it.

## Acceptance criteria

- [ ] With every resolver run verified and the base conflicting again each time, the
      campaign runs the resolver up to `MAX_RESOLVE_RUNS` (4) times and then parks
      `base_moving` (`resume_to: CLOSING`), not `rebase_conflict`.
- [ ] Two failed resolver runs in one CLOSING entry still park `rebase_conflict` with
      today's detail, and a verified run followed by one failed run is retried.
- [ ] `merge.resolver: false` and a missing `pre_head`/`target_sha` still park
      `rebase_conflict` as today.
- [ ] A resolve step whose run would cross `cap_usd` but not `cap_usd +
      resolver_allowance_usd` runs, and appends the "resolver ran on the close allowance"
      finding. Beyond the allowance it parks `cost_cap`. `cost.cap_usd` itself is
      unchanged.
- [ ] `merge.resolver_allowance_usd` validates in the project schema; when absent the
      default is the profile's resolver budget × 2.
- [ ] `wt campaign export --table campaigns` rows carry `rebase_regenerated`,
      `resolver_dispatches`, `rebase_resolved` and `resolver_allowance_usd` (appended
      columns), and existing columns are unchanged.
- [ ] The `/wt-conduct` `parked.rebase_conflict` row no longer describes the
      verified-then-moved case.

## Test plan

- **Automated, `tests/test_agentic_resolver.py`** (the existing SPEC-0221 harness: temp git
  repo, fake runner that writes a resolution, a hook that moves main):
  - `test_verified_runs_then_base_moving_park`: main conflicts again after each verified
    resolution; assert 4 `rebase_resolved` events and a `base_moving` park with
    `resume_to: CLOSING` and the "verified resolutions" detail.
  - `test_two_failures_park_rebase_conflict`: the fake resolver fails twice → a
    `rebase_conflict` park whose detail contains `last:`.
  - `test_verified_then_failed_gets_retry`: verified, base moves, then one failure → a third
    run is dispatched.
  - `test_resolver_opt_out_still_parks` (`merge.resolver: false`).
- **Automated, `tests/test_agentic_queue.py`** (pure `plan_step`):
  - `test_resolve_within_close_allowance` (parametrized): total + budget ≤ cap → `resolve`;
    ≤ cap + allowance → `resolve`; > cap + allowance → `cost_cap` park.
  - `test_allowance_default_and_config`: absent → 2 × resolver budget; configured value is
    used; a negative value fails project validation.
- **Automated, `tests/test_agentic_campaign_export.py`**:
  `test_export_conflict_pressure_columns`: a ledger with 2 regeneration findings, 1
  dispatch, 1 `rebase_resolved` and an allowance overspend gives the four values; the
  column order of existing columns is unchanged.
- **Automated, `tests/test_skills.py`**: `test_conduct_skill_rebase_conflict_row` (no
  "verified" case in the row; `test_conduct_skill_rule_ids` still passes).
- **Sabotage checks:** count verified runs toward `MAX_RESOLVE_ATTEMPTS` again →
  `test_verified_runs_then_base_moving_park` fails; drop the allowance →
  `test_resolve_within_close_allowance` fails.
- **Manual verification:** after merge, `wt campaign export --table campaigns --stdout`
  shows the new columns on the next merged campaigns. Over the SPEC-0298 window,
  `rebase_conflict` parks stay at 0 or are each a real resolver failure. Record both in
  *As shipped*.
- **Regression guard:** full `uv run pytest`; `tests/test_agentic_close.py`,
  `tests/test_agentic_close_regenerate.py` and `tests/test_agentic_gitops.py` unchanged.

   `rebase_conflict` parks since 2026-10-27, and note the figure in *As shipped*.
